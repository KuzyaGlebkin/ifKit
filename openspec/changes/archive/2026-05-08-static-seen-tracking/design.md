## Context

Подсветка `paragraph--unseen` сейчас опирается на `markAndHighlight(element, sceneKey)` и хеши **прямых дочерних** элементов `#scene-content` в хранилище `ifkit:seen` как `Record<sceneKey, string[]>`. Статический контент из `before`/`after` попадает в тот же плоский список узлов и тем же ключом сцены, что и текст сцен — при смене сцены глобальный UI (те же строки состояния) получает другой ключ и ошибочно помечается как новый.

## Goals / Non-Goals

**Goals:**

- Отдельный набор хешей для **статических** блоков (`before` / `after`), общий для всех сцен.
- Для блоков **тела сцены** (включая HTML после подстановки `Slot`) сохранить текущее поведение: учёт по `sceneKey`.
- Старые записи под `ifkit:seen` **не поддерживать как контракт**: достаточно нового формата; если JSON не подходит под ожидаемую форму — пустое внутреннее состояние, без миграции. Игрок при желании сам нажмёт сброс просмотренного.
- Сброс «просмотренного» через `resetSeenContent` очищает оба набора.

**Non-Goals:**

- Менять публичный API `defineGame` / `static` для авторов игр (без необходимости).
- Отдельный учёт per-scene для **slot**-вставок из static: они остаются частью дерева «тела сцены» и остаются per-scene по смыслу (позиция и окружение различаются).
- Миграции CSS авторов под новые обёртки минимально описать (классы без визуала по умолчанию или `display:contents` ниже).

## Decisions

1. **Два статических чанка вокруг тела сцены** — при активном поле `static` в конфигурации игры сборка `#scene-content` SHALL иметь три логических региона в порядке документа: обёртка для `beforeBuffer`, обёртка для сцены (с подстановкой слотов), обёртка для `afterBuffer`. Пустые регионы можно не генерировать. Порядок `textContent` относительно текущего плоского `before + scene + after` сохраняется.

2. **Маркировка регионов для движка** — на каждую непустую обёртку навешать стабильный признак (например `data-ifk-seen-scope="static"` для before/after и `data-ifk-seen-scope="scene"` для среднего блока). Без `static` в игре структура остаётся плоской: один «слоёный» HTML сцены, как сейчас (все прямые дети `#scene-content` только per-scene — без изменений для авторов без static).

3. **`markAndHighlight`** — один вызов на рендер: обойти прямых детей `#scene-content`. Если у ребёнка scope=static — применять хеши к **его** прямым детям против глобального списка `staticSeen`. Если scope=scene — к его прямым детям против `_seen[sceneKey]`. Если атрибута scope нет (legacy) — вести себя как сейчас: все прямые дети только против `_seen[sceneKey]`.

4. **Хранилище** — сохранять в ключе `ifkit:seen` только объект вида `{ scenes: Record<string, string[]>, staticSeen: string[] }`. При чтении: если структура не соответствует (включая устаревший плоский `Record<string, string[]>`) — считать `scenes` и `staticSeen` пустыми; восстановление истории хешей из старых форматов не требуется.

## Risks / Trade-offs

| Риск | Смягчение |
|------|-----------|
| Дополнительные DOM-узлы ломают узкие авторские CSS-селекторы `#scene-content > p` | Использовать обёртки с `display: contents`, чтобы модель дерева форматирования для прямых «визуальных» детей не менялась; задокументировать в задачах проверку. |
| После деплоя у кого-то останется старый JSON или «битые» данные | Старое значение можно отбросить при парсе; восстановление — через явный сброс просмотренного в UI при необходимости. |
| Пустые before/after — лишняя сложность | Не генерировать пустые обёртки. |

## Обновление у игроков

- Явная миграция не делается. После выпуска сборки недействительный или устаревший payload под `ifkit:seen` обрабатывается как отсутствие данных до следующей успешной записи по новым правилам. Нужное поведение «с нуля» по подсветке игрок включает кнопкой сброса просмотренного.

## Open Questions

- Оставить ли `display:contents` для обёрток по умолчанию или полагаться на отсутствие стилей — решается при реализации и визуальной проверке демо-игры.
